# ADR-034: review-html に design・plan の型を足し、同じ作業の資料を 1 枚のページのタブにまとめる

**ステータス**: accepted

**日付**: 2026-10-08

**関連**: [ADR-033](./033-review-html-generalization.md)（未決事項だった「design と plan の型」を本 ADR で決める。ADR-033 の他の決定は維持する）

## コンテキスト

- ADR-033 で、確認画面を汎用の `review-html` にした（requirements と consult の型）。design と plan の型は「architect と planner の出力に固定の番号を付けてから作る」として残していた。
- architect には決まった出力の形がなく、planner の計画には手順・リスク・未決事項の番号がなかった。
- 2026-10-08、ユーザーから「同じタスクに関連する資料は、同じページにタブを分けて作れないか。要件定義書があるなら、そこに仕様書・設計書・実装計画を足していくイメージ」と要望があった。タブでまとめた見本を見たうえで、採用が決まった。

## 決定

### 1. design と plan の型

- architect の出力に、固定の番号を付けた形を足す: 構成 C1、データ M1、API A1、連携とエラー処理 I1、判断 D1（選択肢ごとの良い点・気になる点、推奨と理由）、リスク R1。もとにした要件の番号（S1・S1-AC1・N1）も書く。
- planner の計画に番号を足す: 手順 P1-1、リスク R1、未決事項 D1（任意）。成功条件の番号（N1・E1 など）は今までどおり計画担当の軸の番号を使い、要件の番号は「元の要件」として添えるだけにする。
- 答え方: design は「この設計でよい／直してほしい／要件から見直す／中止する」、plan は「この計画でよい／直してほしい／中止する」。design の「要件から見直す」は要件の段階に戻る。
- `/autorun` の design ゲートは design の型を使う。plan は `/autorun` の中では今までどおり自動で進み、確認画面は単体の `/plan` で使う。

### 2. 1 つの作業 = 1 枚のページ（タブ）

- 同じ作業（機能）の資料は、1 枚のページのタブにする: 要件 → 設計 → 計画。作業に関係する相談もタブにできる。
- 文書 ID は作業ごとに 1 つにする。ポートが同じになるので、段階が進んでも同じ URL で、ブラウザの保存内容も引き継がれる。
- 今決めている段階のタブは「確認中」で、常に最後のタブになる。前の段階のタブは「承認済み」になり、判断欄は承認したときの回答を表示するだけにする。
- コメントは、どのタブにも付けられる。住所にはタブの名前を付ける（例: `design:R1`）。承認済みのタブへのコメントは、済んだ段階への追加の指摘として扱い、戻るかどうかはチャットで確認する。承認済みの段階を、チャットの返事なしに変えることはない。
- 自動保存の指紋は、タブごとに持つ。あるタブの中身が変わっても、変わっていないタブのコメントは残る。コメントは 1 回送ったら、後の回答では送り直さない。
- 段階の途中の相談は、タブにせず、別の文書にする（確認中のタブは常に 1 つで、最後に置くため）。
- 回答の形は version 3 にし、どのタブへの回答か（`tab`）を含める。受け口は変えない（種類と文書 ID の照合のまま）。
- ゲートの承認は、今までどおりチャットでのユーザーの返事だけで決まる（ADR-032・ADR-033 のまま）。

## 結果

### Positive

- 同じ作業の要件・設計・計画を、1 枚のページで行き来しながら確認できる。
- 設計を見ながら、要件の気になる所にもその場でコメントできる。
- 段階が進んでも、前に付けたコメントは消えない。

### Negative

- 1 枚のページが大きくなる。
- タブの切り替えなど、ページの動きの自動テストはない（ブラウザで目視確認する）。
- 段階の途中の相談はタブにできない。
