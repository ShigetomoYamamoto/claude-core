# ADR-033: 確認画面（ADR-032）を汎用にし、1 つのスキルを各段階とチャットの相談で使う

**ステータス**: accepted

**日付**: 2026-10-08

**部分的に置き換える対象**: [ADR-032](./032-requirements-gate-html-confirmation.md)（対象を requirements ゲートだけから汎用に広げる点、スキルの名前、起動のしかた、承認の扱いの場面分け、コメントの付け方。ADR-032 が決めた受け口の安全面、届いた回答をデータとして扱う決まり、役割分担と実行ガードの関係は、本 ADR でも維持する）

## コンテキスト

- ADR-032 に沿って、requirements ゲート専用のスキル `gate-html` を実装した（claude-engineering のブランチ `feature/gate-html-skill_20261008`、コミット `0cff969`、未 push）。
  - 自動テストは node 49 件・python 43 件がすべて通り、2 回のコードレビューで重大な指摘は残っていない。
  - 実際のブラウザで、送信 → 受け口の終了 → Claude への通知の流れと、コメント・判断の記録が動くことを確かめた。
- 2026-10-08、ユーザーから次の要望があった。
  - 段階ごとに別のものを作るのではなく、1 つのスキルを各段階で呼び、場面に合わせた資料を作りたい。
  - `/autorun` を使っていないときも、チャットの文脈から判断して適切な資料を作れるようにしたい。
  - 作る資料はすべて、コメントや回答を付けられるようにする。読むだけの資料でも、追加の質問や指摘が出たときに返せないと困るため。
- 実装の途中で、ADR-032 の書き方から次の点を変えた。本 ADR で正式に記録する。
  - ポートは、文書 ID から毎回同じ番号を計算する。ブラウザの自動保存は「ポートを含む URL の元」ごとに分かれるので、受け口を立て直しても入力を引き継げるようにするため。
  - 合言葉は Claude 側で作って受け口に渡す。起動する前に URL が分かるようにするため。
  - 受け口は、回答を 1 回受け取ったら終了する形で、Bash のバックグラウンド実行で動かす。公式ドキュメントでは、手元の対話セッションのバックグラウンド実行に時間の上限はない（SDK 経由などの無人の実行では既定 30 分）。
  - 判断欄ごとに「ユーザーが選択肢に触れたか」を記録する。1 ページに全部を並べるので「開いたか」は意味を持たないため。
  - 描画した内容の指紋（ハッシュ）を持ち、内容が変わったら前回の入力を捨てる。作り直した資料に古い入力が乗らないようにするため。
  - 描画した HTML に、文書 ID が正しく入っているかを機械で確かめる。食い違うと受け口が回答を断るため。
  - スキルを使う前に、手元の対話セッションか（`CLAUDE_CODE_ENTRYPOINT=cli` と `CLAUDE_CODE_SESSION_ATTENDED=1`）と、必要なファイルと道具（node・open・openssl）があるかを確かめる。どれか 1 つでも違えば、チャットに戻す。

## 検討した選択肢

### 作り方

1. **段階ごとに別のスキルを作る** — 不採用。見た目と操作が段階ごとに分かれ、直す場所も増える。
2. **1 つのスキルで、自由に組んだ部品だけを描く** — 不採用。要件の番号や選択肢の機械チェックがなくなる。要件の番号は、後で計画の成功条件とテストにつながるので、ここを緩めたくない。
3. **1 つのスキルを 2 層にする（土台＋場面ごとの型）** — 採用。

### チャットでの起動のしかた

1. **条件に当たったら自動で作る** — 不採用。小さな相談でも時間とトークンを使う。
2. **明示的に呼んだときだけ作る** — 不採用。使ったほうがよい場面を逃す。
3. **条件に当たったら 1 行で提案し、ユーザーが OK したら作る** — 採用。判断だけをユーザーに頼む原則にも合う。

### コメントの付け方

1. **ブロックごとに「コメント」ボタンを常に表示する**（ADR-032 決定 3） — 不採用。試作で、ボタンが多過ぎて資料の質を下げると指摘された。
2. **本文の文字を選択して付ける。場所は見えない住所と選んだ文字で覚える** — 採用。試作で、選んだ文字とブロックの住所が正しく届くことを確かめた。

### 読むだけの資料の扱い

1. **読むだけの型を作り、受け口を使わない** — 不採用。後から質問や指摘が出たときに、場所を特定して返す手段がない。
2. **作る資料はすべて、コメントと回答を送れるようにする** — 採用。

## 決定

### 1. 名前と置き場所

- claude-engineering に置く 1 つのスキルにする。名前は `review-html` にする（`gate-html` から変える。push の前に変えるので、導入済みのプロジェクトへの影響はない）。
- 開発業務に限る点は ADR-032 と同じ。

### 2. 2 層の作り

- **土台**: 共通の部品（ブロック）を HTML に描く。ブロックは、見出し・段落・箇条書き・表・カード・判断欄・コード・注記。コメント・自動保存・送信・コピー方式は、土台だけで作る。
- **型**: 場面ごとの中身をブロックに直し、その場面で間違えると困る点を機械でチェックする。
  - requirements: 今の内容チェック（番号、未決事項の選択肢 2〜5 個と推奨）をそのまま移す。今回作る。
  - consult（相談）: ブロックの形と大きさだけをチェックする。今回作る。中身の抜け漏れは機械では見つけられない（既知の弱点）。
  - design・plan: architect と planner の出力に固定の番号を付けてから作る。それまでは、design ゲートと単体の `/design`・`/plan` の承認待ちでは consult の型を使ってよい。

### 3. すべての資料にコメントと回答を付ける

- コメントは、本文の文字を選択して付ける（comment-doc と同じ方式）。本文の中にコメント用のボタンは置かない。2026-10-08 にブロックごとの「コメント」ボタンを付けた試作を見たユーザーから、「ボタンが多過ぎて資料としての質を下げている」「選択した範囲に対してコメントを付けられるようにしてほしい」と指摘があったため。ADR-032 決定 3 の「住所付きの部品に付ける方式を基本にし、『+』ボタンを常に見えるようにする」は、この方式に置き換える。
- 常に表示する操作は、画面下の細い帯（「コメント一覧」「回答する」）だけにする。
- すべてのブロックに、見えない住所を持たせる。型が番号を持つブロック（S1、S1-AC1 など）はその番号を、持たないブロックには土台が自動で振った番号を使う。
- コメントには「どのブロックの中の、どの文字か」（住所・選んだ文字・前後の短い文字）を記録する。位置を探し直すときは、そのブロックの中だけを探す。comment-doc では、同じ文が 2 か所にあるとコメントが黙って別の場所に付いたが、探す範囲をブロックに絞ることでこれを防ぐ。見つからないコメントは捨てずに、「場所が見つからないコメント」として残す。
- 判断欄のない資料でも、コメントとひとことを送れる。判断欄は、今までどおり選択肢をクリックして答える。
- 答え方の選択肢は型ごとに決める。
  - ゲート（requirements など）: 「この内容でよい」「直してほしい」「範囲を変える」「中止する」
  - consult: 「この内容で進めてよい」「直してほしい」「質問・指摘を送る」
- 受け口は、どの資料でも起動する。

### 4. 呼ばれる場面と承認の扱い

- **ゲート**（`/autorun` の requirements・design ゲート、単体の `/requirements`・`/design`・`/plan` の承認待ち）: 承認は、今までどおりチャットでのユーザーの返事だけで決まる（ADR-032 決定 2 を維持）。
- **チャットの相談**: 届いた回答は、話を続けるための入力として使う。ただし、届いた回答をもとに元に戻せない操作・外部への送信・実装を始めるときは、先にチャットでユーザーに確認する。受け口からの通知は、ユーザー入力として扱われないため。
- **`/autorun` の自動で進む段階**（analyze-task・plan・tdd・verify など）: このスキルは使わず、提案もしない。提案すると、そこが新しい停止点になり、「ゲートは段階の性質から決まる」決まり（`loop-safety.md`）に反するため。

### 5. チャットでの提案

- スキルの説明文に、提案の条件を書く。次のどれかに当たる回答をするときに、「HTML にしますか？」と 1 行で提案する。
  - ユーザーに判断を 3 件以上求める
  - 案を比較する
  - 長い文書になる（目安: 見出しが 3 つ以上、または 40 行を超える）
- ユーザーが OK したら作る。同じ話題での提案は 1 回までにする。
- 手元の対話セッションかどうかの前提チェックは、どの場面でも必要。条件に当たらない環境では提案もしない。

### 6. 受け口の変更

- 受け口が確かめる回答の種類を、型によらない形にする（文書 ID の照合は維持する）。受け口を変えたら、コードレビューを通す。
- それ以外の受け口の安全面（127.0.0.1 だけ・合言葉・Host と Origin の照合・256KB の上限・ファイルを書かない・1 回で終了）は ADR-032 のとおり維持する。

### 7. 入口と判断者

- このスキルは、見せて回答を集める役だけを持つ。要件・設計・計画の中身を決めるのは、今までどおり requirements-analyst・architect・planner。
- チャットの相談で作る資料は、Claude がその時点で出している回答を見せるもの。資料を作ること自体で、何かが決まることはない。
- HTML と JSON の書き出しは executor に任せる（ADR-032 と同じ）。

## 結果

### Positive

- どの場面でも、同じ見た目と操作で資料を読み、コメントと回答を返せる。
- 型を 1 つ足すだけで、使える場面を増やせる。
- 読むだけのつもりの資料にも、質問や指摘を場所付きで返せる。
- 要件の機械チェックと、ゲートの承認の確かさは下がらない。

### Negative

- consult の型は、中身の抜け漏れを機械で見つけられない。
- 資料を作るたびに受け口を起動する。
- 提案するかどうかは Claude の判断に頼る。説明文で条件を示すだけで、機械では強制できない。
- design と plan の型は、まだない。
- `gate-html` から `review-html` への名前の変更が要る。

## 未決事項

- design と plan の型の中身と、作る時期
- 「長い文書」の目安を使ってみて調整するか
- セッションを閉じた後で答える場合の扱い（ADR-032 から引き続き未決）
