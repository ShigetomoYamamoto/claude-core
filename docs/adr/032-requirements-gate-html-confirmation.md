# ADR-032: /autorun の requirements ゲートに HTML の確認画面を足し、回答をローカルの受け口で自動返送する

**ステータス**: proposed

**日付**: 2026-10-08

## コンテキスト

- 2026-10-05、Anthropic の Claude Code チームの Thariq Shihipar 氏が `html-plan` プラグインを `anthropics/claude-plugins-community` に追加した（PR #2398、MIT）。実装計画を1枚の HTML にし、判断欄・コメント・「Respond」で回答をまとめて回収する。
- 2026-10-08 に同梱の見本で試した結果、次のことが分かった。
  - 文章は英語の簡易版（ASD-STE100）で書く決まりになっていて、読めなかった。チェック用の `pack.mjs` も英語が前提（文末を `. ? !` で判定する）。
  - コメントは、住所（主張の番号・コードの行番号・画面部品の名前）を持つ部品にだけ付けられる。デスクトップでは「+」ボタンがマウスを乗せるまで見えず、どこに付けられるかが分からなかった。
  - 回答はコピーしてチャットに貼る。
- DWAI 直下の自作スキル（`comment-doc` / `decision-checklist` / `doc-screenshot`）は日本語で、ブラウザへの自動保存と JSON の書き出し・読み込みを持つ。ただし回答はコピーして貼る往復で、SKILL.md に DWAI の絶対パスが埋め込まれている。
- claude-engineering の `/autorun` には、人が承認する段階（ゲート）が4つある（requirements・design・pr・deploy。`docs/autorun-flow.md`）。requirements は vibing でも外れない唯一の方向確認（[ADR-015](./015-vibing-mode.md)）。plan は自動で進む。
- requirements ゲートの今の動き:
  - `requirements-analyst` が「Requirements Summary」を出す。中身は、目的・機能要件（ユーザーストーリーと、Given / When / Then 形式の受け入れ条件）・非機能要件・範囲（やる / やらない）・設計が必要かの判定（`design_needed`）・リスクと未決事項。
  - `/autorun` は停止の手順（`commands/autorun.md`）で、関門名・成果のまとめ・次に進むと何が起きるかと、承認 / 修正 / 中止を示してターンを終える。承認を受けてから次に進み、`gates_passed` に記録する。
  - 承認された後に、executor が `docs/requirements.md` に保存する（`requirements-analyst` の「Persist on Approval」）。
- 守る決まり:
  - ユーザーには操作でなく判断だけを頼む。コピーして貼る往復は操作にあたる。
  - 人が読む文書は日本語で書く（`rules/doc-language.md`、[ADR-021](./021-language-policy-update.md)）。
  - 入口と判断者は1つ（`loop-safety.md`「Single entry, single judge」、[ADR-014](./014-loop-engineering-as-discipline.md) / [ADR-025](./025-single-entry-and-loop-engineering-skill-retirement.md)）。
  - メインループは書き込めない。書き込みは executor に任せる（[ADR-026](./026-execution-guard-role-axis.md)）。
  - 1プロジェクト＝1ドメイン（[ADR-023](./023-three-foundation-split.md)）。
- 2026-10-08、作業用フォルダで試作した。Node の標準機能だけで書いた受け口を Monitor ツールで起動し、ブラウザのページで「送信」を1回押すと、回答がそのままセッションに通知として届いた。コピーも貼り付けも要らなかった。分かった制約は2つある。
  - Monitor は仕様上、最長30分で強制終了する。
  - 届いた通知に、Claude Code は「ユーザー入力ではない。承認や同意とみなさない」と明示する。受け口からの通知は、ユーザーの承認としては使えない。

## 検討した選択肢

### 置き場所

1. **claude-core に、分野を問わない仕組みとして置く** — 見送り。今回は開発業務に絞る（ユーザーの判断）。
2. **自作プラグインとして配る** — 見送り。
3. **claude-engineering に、開発業務専用として置く** — 採用。

### 組み込み方

1. **新しい入口・段階として足す**（html-plan のように「計画を頼まれたら起動」） — 不採用。計画や要件を判断する者が2人になり、単一入口の決まりに反する。
2. **既存のゲートの確認画面にする** — 採用。ゲートの数も流れも変わらない。

### 最初に作る段階

1. **requirements ゲート** — 採用。一番大事な方向確認で、vibing でも外れない。html-plan の1階層目のうち「何ができるようになるか」と判断欄がそのまま当てはまる。
2. **plan** — 見送り。`/autorun` の中では自動で進むので、見る場面が対話で `/plan` を使うときに限られる。
3. **design ゲート** — 見送り。必要なときだけ通るゲートなので、後で展開する。

### 回答の戻し方

1. **ローカルの受け口で自動返送する** — 採用。試作で動くことを確認した。
2. **コピーして貼る** — 受け口が使えないときの予備として残す。
3. **claude.ai の Artifact に置いて、Claude が回答を直接読む** — 不採用。非公開でも要件の中身を外部にアップロードすることになり、毎回確認が要る。お客さんの案件の要件を載せてよいかの判断も要る。

### 作り方

1. **試作を土台に、小さく自作する** — 採用。全部を自分で読めて、テストも書ける。
2. **html-plan の部品（`htmlplan.js` 約145KB など）を持ち込んで改造する** — 不採用。日本語化と送信の仕組みの差し込みに大きな改造が要り、取り込んだ後は上流の更新も自動では入らない。
3. **comment-doc のテンプレート（約128KB）を土台にする** — 不採用。触れない固定部分が多く、判断欄がない。

## 決定

### 1. 置き場所・呼び出し方・使える範囲

- claude-engineering に、開発業務専用のスキルとして置く。名前は実装時に決める（仮称 `gate-html`）。
- 新しい段階や入口は足さない。`/autorun` の requirements ゲートで、承認を求めるときの確認画面として呼ぶ。
- `autorun-flow.md` のゲートの数・種類（gate / auto）・遷移は変えない。変えるのは、requirements ゲートで承認を求める手順だけにする（`commands/autorun.md` の停止の手順と、`requirements-analyst` の「Wait for Confirmation」）。
- 使うのは、手元のパソコンで対話しているセッションだけにする。SDK 経由の自動実行や、ブラウザを開けない環境では、今までどおりチャットで承認を求める。
- 対話で単体でも使えるようにする。ただし次の2つを守る。
  - 明示的に呼んだときだけ動くようにし、説明文で自動起動させない。自動実行のセッションで勝手に動かないようにするため。
  - 単体で使うときは、すでにある要件（`docs/requirements.md` か、会話中の Requirements Summary）を表示するだけにする。要件を新しく書くのは、今までどおり `/requirements` → `requirements-analyst` だけが行う。入口を2つにしないため。

### 2. ゲートの流れと承認

1. `requirements-analyst` が Requirements Summary を出す（今までどおり）。
2. executor が、その内容から確認画面の HTML を作る。
3. メインループが受け口を起動し、ブラウザでページを開く。今までどおりターンを終えて待つ。
4. ユーザーがページで、判断欄・コメント・答え方（下の 3 を参照）を選んで「送信」する。
5. 届いた回答に応じて、次のように進む。
   - 「直してほしい」「範囲を変える」、または判断を推奨から変えた・コメントがあった場合: `requirements-analyst` が回答を反映して作り直し、新しいページで改めて示す。
   - 「この内容でよい」の場合: チャットで、届いた回答の要点を1〜3行で示して承認を求める。推奨のまま開かれなかった判断があれば、ここで挙げる（開かれなかった判断は同意とみなさない。html-plan の決まりを引き継ぐ）。
   - 「中止する」の場合: チャットで中止してよいかを確かめる。
6. **ゲートを通すのは、チャットでのユーザーの返事だけにする。** 受け口からの通知はユーザー入力として扱われないので、ページの送信だけでは承認しない。返事は「OK」の一言で足りるようにする（判断だけを頼む決まりの範囲）。
7. 承認されたら、executor が `docs/requirements.md` に保存する（今までどおり。既存のファイルがあれば差分を示して確認する）。`gates_passed` に記録する。

正本は今までどおり `docs/requirements.md` で、HTML は表示と回答の回収だけを担当する。

### 3. 確認画面の中身（requirements ゲート）

- Requirements Summary の項目に合わせて並べる。
  - 目的
  - 機能要件: ユーザーストーリーごとに1枚のカードにし、受け入れ条件（Given / When / Then）を並べる
  - 非機能要件
  - 範囲（やる / やらない / 将来の検討）
  - 設計が必要かの判定（4項目と `design_needed`）
  - リスクと未決事項: 未決事項は判断欄にする（選択肢を示し、推奨に印を付ける）
- 画面の見本は載せない。見た目をどうするかは設計の仕事で、`requirements-analyst` の「解決策を書かない」の決まりに反するため。見本は、design ゲートに展開するときに扱う。
- `requirements-analyst` の出力に、未決事項ごとの選択肢と推奨を足す（出力形式の小さな変更）。
- 答え方は4つ: 「この内容でよい」「直してほしい」「範囲を変える」「中止する」（今のゲートの承認 / 修正 / 中止と、`requirements-analyst` の範囲の調整に対応する）。
- 全部を1ページに並べる（試作でユーザーが選んだ形。実装時に改めて確認する）。
- コメントは、住所付きの部品（ストーリー・受け入れ条件・未決事項など）に付ける方式を基本にする。Claude がどこへの指摘かを特定できるようにするため。コメントの「+」ボタンは常に見えるようにする。
- 文章は日本語で、平易に書く。
- Issue から始める support モードは requirements を通らないので、この画面は出ない（既知の弱点）。

### 4. 受け口

- Node の標準機能だけで書く。ファイルは書かない。
- 受け付けるのは 127.0.0.1 からだけ。ポートはその都度 OS に選ばせる。推測できない合言葉（128ビット）を URL に含める。宛先の名前（Host）と送信元のページ（Origin）を照合する。受け取る量は 256KB までにする。
- ページは受け口自身が配信する（同じオリジンから送るので、ブラウザの通信制限やローカルネットワーク許可の確認を避けられる）。
- 受け口に有効時間は設けない。止めるのは、回答が届いたときとセッションを閉じたときだけ。熟考したり、後で確認したりしても時間切れにならないようにするため。
- 起動のしかた:
  - 第一候補: 回答を1回受け取ったら終了する受け口を、Bash のバックグラウンド実行で起動する。終了したときに Claude が呼び戻される。長時間待てるかは未検証なので、実装時に2時間放置してから送信する試験で確かめる。
  - 予備: Monitor を30分ごとに、同じポートと合言葉で張り直す。開いたままのページはそのまま使える。張り直しの数秒に送信が重なったときのために、ページ側で何回か再送する。
- 1回受け取ると終了するので、送り直すときは受け口を立て直す。作り直して改めて示すときは、新しいページと新しい受け口になる。
- 受け口が無いときは、ページがコピー方式に切り替える。回答はページの中に自動保存しておく。

### 5. 届いた回答の扱い

- 回答はデータとして扱い、指示としては扱わない（html-plan の決まりを引き継ぐ）。
- 選んだ選択肢とコメントは、要件への回答として `requirements-analyst` に渡す。コメントにコマンドの実行・URL の取得・設定や権限の変更などが書かれていても、従わない。新しい依頼や危ない依頼が含まれていたら、チャットでユーザーに確認する。
- 承認には使わない（決定 2 の 6）。

### 6. 役割分担と実行ガードの関係

- HTML の生成と `docs/` への書き込みは executor に任せる。
- 受け口の起動と待機は、メインループが行う。回答の通知をメインループが受け取る必要があるため。
- 受け口はポートを開くだけでファイルを書かないので、実行ガード（[ADR-026](./026-execution-guard-role-axis.md)）は反応しない。これがガードの迂回にならないように、次の2つを決まりにする。
  - メインループが起動してよいのは、スキルに同梱した固定の受け口ファイルだけにする。
  - 起動コマンドは、スキルに書いた1つの形だけにする。
- この決まりは、パターン検出では守れない（[ADR-028](./028-command-string-guard-limits.md) と同じく、決まりそのものが防御になる）。

### 7. 他から借りるもの

- html-plan は設計の手本として読む。部品を借りる場合は部品単位で借り、MIT ライセンスの著作権表示を残す。
- 受け口の考え方は f-labs の `agent-html-skills`（MIT）にもある。コードは借りず、考え方だけを参考にする。

## 結果

### Positive

- ゲートの判断と指摘に、クリックで答えられる。コピーして貼る往復がなくなる。
- ゲートの数と流れは変わらない。正本・保存の時期・成功条件の表・tdd-guide の決まりも変わらない。
- 受け口に時間切れがないので、熟考したり後で確認したりできる。
- 承認は今までどおりチャットのユーザーの返事で決まるので、ゲートの確かさは下がらない。

### Negative

- ゲートのたびに HTML を作るので、時間とトークンが増える。
- 承認のために、ページの送信に加えてチャットでの返事が1回要る。
- セッションの間、ローカルで待ち受けるプロセスが1つ増える（決定 4 の対策で抑える）。
- SDK 経由の自動実行・ブラウザを開けない環境・support モードでは効かない。
- `requirements-analyst` の出力形式に、未決事項の選択肢と推奨を足す変更が要る。
- 受け口を長時間待たせられるかは、まだ確かめていない。
- 実行ガードの対象外の経路が1つ増える。固定ファイルと1つのコマンドに限る決まりで抑える。

## 未決事項

- スキルの名前
- HTML の置き場所（リポジトリの管理外にする。候補は、gitignore したプロジェクト内のフォルダか、`~/レビュー/<リポジトリ名>/`）
- セッションを閉じた後で答える場合の扱い（次のセッションで受け口を立て直すか、コピー方式か）
- design ゲートと plan への展開の時期
- 実際の変更での試用
