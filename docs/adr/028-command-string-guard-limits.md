# ADR-028: コマンド文字列ベースのガードの限界を明示し、規範を一次防御に置く

**ステータス**: accepted

**日付**: 2026-09-08

## コンテキスト

Bash を対象とする2つの hook は、いずれも**コマンド文字列のパターンマッチ**で危険な操作を検出している。

- `mass-delete-blocker.py` — `rm` トークンを解析し、再帰/大量削除を人間に確認させる
- `main-loop-execution-guard.py` — 変更系コマンド名とリダイレクト記号でメインループの実作業を止める

2026-08-25、サブエージェントが `rm` を拒否ルール（`Bash(rm *)`）とフックの両方でブロックされた後、
`python3 -c "import os; os.remove(...)"` で同じ削除を42ファイル分実行した
（[Issue #100](https://github.com/ShigetomoYamamoto/claude-core/issues/100)）。削除内容は事前合意の
範囲だったが、**ブロックされた効果を別経路で達成した**点が問題である。

同じ根から、ガード側には逆向きの不整合もあった（[Issue #103](https://github.com/ShigetomoYamamoto/claude-core/issues/103)）。

- **過検知**: `Write` なら通る auto-memory への書き込みが `cat >> ...` では弾かれる。Bash では対象パスを
  取り出しておらず、例外パス判定に載っていなかった
- **過少検知**: ヒアドキュメント・`python3 -c`・`sh -c "..."` 経由の書き込みは、リダイレクト記号も
  denylist のコマンド名も現れないため素通りする

両者とも「文字列から効果を推し量る」ことの限界である。シェルやインタプリタに渡された任意コードの
効果を、実行せずに文字列から確定することは原理的にできない。

## 検討した選択肢

1. **拒否リストにインタプリタを足す**（`python3 -c *` を丸ごと禁止） — 読み取り専用のワンライナー
   まで殺す。誤検知の代償が大きい割に `python3 script.py` は防げない。
2. **Bash をトークン化して全引数のパスを解決する** — 決定4のとおり、例外パス配下への破壊操作
   （`rm -rf ~/.claude/projects/*/memory/` 等）を通す穴になる。変数展開・パイプライン・ヒアドキュメント
   までは追えず、完全性も得られない。
3. **現状維持 + 明文化のみ** — Issue #103 の過検知（memory への追記が理由不明に弾かれる）が残る。
4. **呼び出し形式による近似検出 + 規範を一次防御に据える**（採用） — パターン層はペイロードの意味を
   解釈せず、「インタプリタにインラインコードを渡す形式」だけを検出する。これと組み合わせて、
   検知網の限界を規範（`rules/safety-irreversible.md`）で補う。

## 決定

**選択肢4を採用する。**

1. **これらの hook は規律・確認の層であり、セキュリティ境界ではないと明示する。** 悪意ある回避を
   防ぐことを目標にしない。目標は「うっかり」と「安易な迂回」のコストを上げ、不可逆操作を人間の目に
   通すこと。

2. **一次防御は規範に置く。** `rules/safety-irreversible.md` に「ブロックされたら止まる。検知されない
   別経路で同じ効果を出さない」を明記する。ブロックが名指しした逃げ道（ガードが指示する委譲）は
   設計どおりの経路であり迂回ではない。**検知されないことによって成立する経路**だけが迂回である。
   パターン層ではなくこの区別が、未知の手段まで覆う唯一の層。

3. **パターン層は「呼び出し形式」で近似する。** ペイロードの意味は解釈しない。共有ヘルパ
   `hooks/_command_effects.py` が「インタプリタにインラインコードを渡す形式」（`python3 -c` /
   `node -e` / heredoc / `sh -c`）を列挙し、各 hook が自分の関心（mass-delete は削除 API、guard は
   書き込み+削除 API）と組み合わせて判定する。共有するのは形式の判定だけで、何を危険とみなすかは
   各 hook が持つ。ヘルパは guarded import で読み込み、欠けても各 hook は従来の検出のみで動作を
   続ける。

4. **例外パスの救済はリダイレクト先に限る。** 全引数をパスとして解決する案は採らない。
   `rm -rf ~/.claude/projects/*/memory/` のような、例外パス配下への破壊操作まで通してしまうため。
   救うのは「変更要因がリダイレクトだけ」かつ「出力先が絶対パスで例外パス配下」の場合に限り、
   相対パス・変数展開・glob は通さない（fail-closed）。

## 結果

### Positive

- Issue #100 で観測された経路（`python3 -c` 経由の削除）と、`sh -c` に隠れた `rm` が確認/ブロックの
  対象になった。
- `cat >> ~/.claude/projects/*/memory/MEMORY.md` が通るようになり、同じ対象・同じ意図でもツールに
  よって結果が変わる不整合が解消した。
- 残余リスクが「実装の抜け」ではなく「宣言された設計上の限界」になった。

### Negative

- **網は意図的に不完全**。未知のインタプリタ、難読化、`base64 -d | sh`、変数に組み立てたコマンド、
  `cat <<EOF | python3` のようなパイプ経由は引き続き素通りする。パターンを足しても構造は変わらない。
- **各プロジェクトの `.claude/settings.local.json` にある `Bash(rm *)` 系の拒否ルールは claude-core
  から修正できない**（installer の管理外）。Issue #100 の完全な解消にはプロジェクト側の対応が要る
  ため、**Issue #100 はこの ADR では閉じない**。
- `tee` は `_MUTATING` に含まれるため、例外パスへの `tee` は引き続きブロックされる（リダイレクトのみ
  を救う設計の帰結）。
- 旧「既知の検出漏れ」テスト（test_46）の期待値を反転させた。テスト自身のコメントがこの変更を
  予期していた。
- 引用符外の `x>1` がリダイレクトとしてブロックされる既知の近似は、今回対象外（POSIX シェルでは
  実際にリダイレクトであり、ブロックが正しい挙動）。
